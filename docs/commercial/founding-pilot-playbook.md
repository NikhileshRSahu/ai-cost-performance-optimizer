# Founding Pilot Onboarding Playbook

## Goal

Turn one customer-owned evidence set into one credible optimization decision with the smallest possible trust requirement.

## Ideal pilot customer

Prefer teams that:

- spend enough on AI for one optimization to matter,
- can export request- or aggregate-level usage,
- have at least one repeated workload,
- can state a quality/performance requirement,
- can identify a technical owner who can implement or validate a change.

Do not require provider administrative credentials for the CSV-first pilot.

## Pilot offer

### CSV Efficiency Check — free

Purpose: prove the system can understand the customer's evidence before asking for money or deeper access.

Deliver:

- AI Work MRI,
- data-quality limitations,
- top measurable inefficiency signals,
- whether a benchmarkable opportunity exists.

### Optimization Audit — $299 one-time founding price

Deliver:

- one prioritized optimization hypothesis,
- evidence and uncertainty,
- explicit quality/latency/failure constraints,
- controlled benchmark,
- OPTIMIZE / DO_NOT_CHANGE / INSUFFICIENT_EVIDENCE decision,
- implementation package and rollback criteria,
- decision-ready report.

### Verified Optimization Sprint — from $999

Deliver the audit plus:

- implementation support,
- staged rollout guidance,
- post-change evidence window,
- verified net-impact calculation,
- prediction-versus-actual review.

Do not promise a fixed saving percentage.

## Intake

Ask only for what is necessary:

1. one usage CSV,
2. reporting currency,
3. the workload to optimize,
4. success/quality definition,
5. maximum acceptable latency/failure thresholds,
6. who will approve implementation.

Optional sanitized AI-history evidence can be requested only when prompt/context/workflow analysis would materially improve the decision.

## First customer meeting

The meeting should answer three questions:

1. What outcome matters?
2. What must not get worse?
3. What evidence can the customer share comfortably?

Avoid starting with provider architecture or a feature tour.

## Work MRI review

Present in this order:

1. strongest evidence-backed fact,
2. strongest opportunity,
3. principal uncertainty,
4. safest next test,
5. what additional evidence would unlock.

Do not show unsupported metrics as zeros.

## Benchmark gate

Before running a benchmark, record:

- baseline configuration,
- candidate configuration,
- representative evaluation set,
- minimum quality,
- maximum latency where relevant,
- maximum failure rate,
- cost measurement method.

A cheaper candidate that misses a hard requirement is DO_NOT_CHANGE.

## Implementation gate

Before implementation provide:

- exact intended mechanism,
- affected workload,
- staged rollout,
- rollback trigger,
- rollback instructions,
- verification window.

The customer approves production change.

## Verification gate

Never label savings VERIFIED until:

- implementation evidence exists,
- post-change evidence is comparable,
- required performance remains within bounds,
- net financial impact is calculated from supported evidence.

Negative impact stays visible.

## Sales proof capture

With explicit written permission, record only:

- customer type and workload category,
- baseline cost range if approved,
- tested change,
- quality/latency outcome,
- verified net impact,
- implementation complexity,
- quote/testimonial if approved.

Do not publish customer prompts, proprietary content, or identifying usage details without explicit permission.

## Support boundaries

For a pilot, support should cover:

- CSV format troubleshooting,
- evidence interpretation,
- benchmark design,
- implementation-package questions,
- verification setup.

Connected Gmail/Drive/Slack/AI-history OAuth support is outside the CSV-only production pilot until connector security gates are complete.
